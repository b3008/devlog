## Glossary

- **Sentinel block** — the `<!-- DEVLOG:START -->` / `<!-- DEVLOG:END -->`-wrapped section injected into an agent's context file. Must stay deterministic so re-installs produce clean diffs.
- **Convention** — the markdown text rendered from `config.yaml` and dropped inside the sentinel block.
- **Tag discovery** — the install-time scan of `blog/*.md` frontmatter that unions discovered tags into the rendered vocabulary.
- **Self-tailoring** — the convention's instruction to the agent to propose `config.yaml` edits when the defaults don't fit the project's domain.

## Entities

- `.devlog/config.yaml` — user-owned stable configuration (triggers, voice, tags, frontmatter, media).
- `.devlog/learned.md` — this file. Agent-owned adaptive surface.
- `.devlog/manifests/<agent>.manifest.json` — SHA-256 tracking per agent install. Includes `hooks` and `commands` arrays.
- `convention.py` — renderer plus `discover_tags()` and `scan_entries()` helpers.
- `manifest.py` — install manifest model. Kept intentionally small.
- `templates/commands/*.md` — slash command bodies, copied into the agent's commands dir (`.claude/commands/`, `.opencode/commands/`) on capable installs. Drop-in: any new `.md` here gets installed automatically (glob). As of 0.4.0 there are **four**: `catchup` / `write` / `manicure` (the authoring loop) + `upgrade` (maintenance). Format is the cross-agent common denominator: markdown body + `description` frontmatter + `$ARGUMENTS` — verified to work verbatim in both Claude Code and OpenCode.
- `AgentConfig` capability fields (0.5.0) — `commands_dir`, `global_dir`, `supports_hooks` on the registry entry drive the install pipeline; no `key == "claude"` gates remain except claude-only history (the `~/CLAUDE.md` legacy sweep). Adding a first-class agent = one registry entry + doc-verified paths. Global paths derive as `~/{global_dir}/{context_file}` and `~/{global_dir}/commands`. OpenCode: `.opencode/commands/` (plural — doc-verified), `~/.config/opencode/`.
- `devlog upgrade` (0.3.0) — two-layer self-upgrade: upgrades the tool binary (via `_detect_install_method`), then re-invokes the *freshly installed* binary as a subprocess to resync the repo's convention. `--check`/`--project-only`/`--tool-only`. Subprocess seams (`_run_tool_upgrade`, `_run_resync`, `_query_version`) are isolated for monkeypatched tests. `__main__.py` is the `python -m devlog_cli` fallback entry point.
- `/devlog-upgrade` (slash command, 0.4.0) — thin AI driver over the `devlog upgrade` CLI. Preflight `command -v devlog`; run `devlog upgrade --check` to read the install-method-aware preview; then apply (self-upgradeable) or handle the named fallback (source → `git pull`; uvx → persistent install). Property worth remembering: **upgrade pulls what's on the git *default branch*; `install` pulls what's *local*** — so a new template can't be bootstrapped via the upgrade path until it's on `main`. (Sharpened 2026-07-31: "published/pushed" was too loose — the `uv tool` receipt pins only `git = "…/devlog.git"`, no branch or tag, so a release sitting on an unmerged branch is invisible. When `main` lags the branch, `uv tool upgrade devlog` *downgrades* — measured 0.3.0 → 0.2.0 — and reports it as a normal install.)

## OKF (Open Knowledge Format)

- **OKF v0.1** ([spec](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf)) — Google's vendor-neutral format: directories of markdown + YAML frontmatter as portable knowledge bundles. Only hard requirement is a non-empty `type` per concept doc; consumers MUST tolerate missing optional fields, unknown keys, broken links, and missing index. devlog was ~90% OKF-shaped already — conformance (shipped 0.5.0) was mostly field renames.
- **Entry = OKF concept document.** Frontmatter leads with `type: "Devlog Entry"`; `summary` was renamed to OKF's canonical `description` (its index/snippet field). `date`/`timestamp` are devlog extras OKF tolerates.
- **Index = OKF bundle root.** `_index.md` → reserved `index.md`; `build_index()` stamps `--- okf_version: "0.1" ---` (the one place OKF allows frontmatter on an index) and its heading scan skips a leading frontmatter block. The old `_` prefix (sort-first) was the single thing making the bundle non-conformant.
- **`devlog migrate`** (0.5.0) — idempotent OKF migration for existing blogs. `plan_migration() → MigrationPlan` is the **single source of truth** shared by `migrate`, `status`, and `install`; `_apply_migration()` mirrors its decisions. Auto-runs inside `_install_local` (the upgrade path) so legacy blogs self-heal. `migrate_entry_text()` does raw-line frontmatter edits (NOT yaml round-trip) to preserve order/comments/quoting. Must migrate the config `frontmatter` *list* too — the convention is generated from it, so a stale list keeps emitting non-conformant entries. This is the project's first real schema-migration story (the 06-12 open thread asked for one).

## Recurring themes

- **Stable surface + adaptive surface.** The sentinel block is pinned and idempotent; `learned.md` and discovered tags carry anything that would otherwise make re-installs noisy. When adding new adaptivity, prefer pointers to external files over dynamic rendering into the sentinel block.
- **Case-study-driven design.** Feature additions on this project tend to come from observing the convention fail on a real project, rather than from up-front speculation. That framing belongs in blog entries when it applies.
- **Self-referential dogfooding.** devlog is installed on itself, so its own blog is both a test bed and a live example. Entries here should read as genuine project reflections, not demos.
- **Canonical public positioning (README, 2026-06-13):** lead with the durable, git-versioned, cross-agent *why-record* as the real product; the portfolio blog is its human-facing rendering. Capture is framed as best-effort (firmer with the `Stop` hook), never infallible. Keep messaging consistent with this ordering. The README's most persuasive copy is its most candid — an adversarial honesty-skeptic pass improved it by *removing* marketing (cut "walk away with four things", "Every … is captured", "navigable").
- **Dogfooding the warm path.** Self-installing devlog on this repo doesn't exercise cold-start failure modes — this repo always has scaffolding present. New surfaces (slash commands, hooks) need explicit cold-repo verification or external review (e.g. PR #9's Copilot review caught the missing-scaffolding gap that local dogfooding could not).
- **"Trivial" is about reusable insight, not diff size.** A one-line README logo swap (2026-06-13) looked too small to log, but it carried a design *decision* (four candidate fonts → ANSI Shadow) and a reusable method (deterministic ASCII via `uvx pyfiglet`, which sidesteps the LLM alignment failure mode of hand-rolled art). The Stop hook caught the skip. When judging triggers, weigh the insight that would be lost, not the size of the change.
- **Slash commands as thin drivers over CLI verbs.** The highest-leverage slash command isn't one that reimplements logic — it's one that runs an existing CLI in preview mode (`--check`), *reads the install-method-aware output*, and branches on it (offer `git pull` for a source checkout, suggest a persistent install for uvx). The CLI stays the single source of truth; the slash command adds the judgment a flag-parser can't. `/devlog-upgrade` (0.4.0) is the worked example.
- **The convention governs report style, not just write behavior.** v0.4.1 added an opener instruction telling the agent to announce a write with just the file path and to say nothing when no entry is warranted — fixing the per-turn "I checked these triggers and scaffolded X…" narration. The lesson: when the agent does something annoying *around* the devlog, the lever is usually a sentence in `generate_convention()`, not a code change. (Em-dash gotcha: template f-strings use `—` escapes to stay ASCII; `DEFAULT_CONFIG` data strings use literal `—`. Match the immediate neighbor.)
- **The read limit is tokens, not bytes — and density decides the conversion.** A file read returns at most ~25k tokens; past that you get a *truncated page* that is indistinguishable from success (hard refusal only at ~256KB). Prose runs ~4 bytes/token but `learned.md`-style notes (backticked identifiers, paths, code fragments) measured **2.5**, so 25k tokens can arrive at ~60KB where a byte estimate promises 100KB. Any byte budget over agent-read files must be set pessimistically or it stays silent through the whole window where reads are already truncating.
- **Subtraction has a floor; structure is what's below it.** Trimming the 467KB `learned.md` got 87%/88% cuts from Glossary and Open threads (narration the blog told better) but only **15%** from Recurring themes — durable API gotchas, 129 of 148 kept verbatim. When the irreducible part is still too big, the fix is decomposition (index of one-line hooks → `.devlog/knowledge/`), not more trimming. Flat files load all-or-nothing; an index costs the same regardless of what's behind it.
- **A hook is the load-bearing part of an index, not decoration.** `- [Title](knowledge/slug.md) — what's inside` : without the clause a reader can't triage, so they load everything (no gain) or nothing (knowledge now *invisible*, where an oversized flat file at least still greps). A **stale** hook is worse than a missing one — it misroutes triage actively. Hence the `/devlog-manicure` dimensions for drifted hooks and unindexed files.
- **One field, two questions — the overload that ate a customization (0.6.0).** Manifest `sha256` meant both *"what is on disk"* (uninstall: only delete what I recognise) and *"what did devlog write"* (install: detect user edits). They coincide until the first preserve — which records the *user's* hash — and diverge forever after, so the next template change reads "unchanged since install" and silently destroys the customization the previous run protected. Protection expired exactly at the next release. Fixed by splitting out `source_sha256`, updated only when devlog actually writes and carried forward on preserve; baseline falls back to `sha256` for legacy manifests (additive field, self-heals on reinstall, pinned by a test). Uninstall still reads `sha256` — correct, but it's the same overloading, so look before adding the next field.
- **Read the code before writing the entry.** The 07-29-02 entry described `install`'s preservation check as "file vs shipped template" from reading its *output*; it is actually a three-way comparison (file vs manifest install-time hash vs new template), so untouched-but-stale files already resync. The output was accurate, the inference wasn't. Cost: a published mischaracterisation needing a dated correction. Devlog entries assert things about code — verify against the source, not the terminal.
- **Three install layers drift independently; no command sees all three (2026-07-31 fleet audit).** Tool binary (`uv tool`, tracks the default branch), global convention block (`~/.claude/CLAUDE.md`, its own version stamp), and per-repo data (blog index name, entry frontmatter, config). Measured skew across 25 installs: binary 0.3.0, global block **v0.4.1** (newer than the binary — injected by a dev venv build), 24/25 repos still pre-OKF. `_install_local` auto-migrates but only in cwd; `status` is cwd-scoped too. So drift is individually detectable and collectively invisible — the layer count, not the version count, is what makes "do I need to reinstall?" hard to answer.
- **Config is the wrong sole authority for a filename the filesystem can answer (0.6.1).** `plan_migration()` took the index name from `config["index_file"]` alone; a repo scaffolded by the *global* convention has no `.devlog/config.yaml` (global install never writes one), so the default resolved to `index.md`, the real `_index.md` was invisible, and migrate wrote a second index while orphaning the first — which then counted as a blog entry forever, being absent from `skip`. 16 of 24 fleet repos were in that state. Fix is a disk probe when the configured name doesn't exist; everything downstream reads `plan.current_index`, so one substitution fixed all three symptoms. Companion rule: **a dry run must not promise work it will decline** — `config_update` was reporting a config rewrite in projects with no config, so it's now gated on an `index_file:` key existing.
- **A preserve pins one artifact while its siblings move (first live `--force`, 2026-07-31).** The global resync flagged 3 slash commands + `stop.py` as "customized"; diffing showed *zero* personal edits — every line was template evolution (`_index.md`, the 100KB budget, pre-`knowledge/` wording). Stale 0.4.x files, indistinguishable from edits by hash alone. Visible symptom: the freshly-written v0.6.0 convention block said `blog/index.md` while the preserved commands beside it still said `blog/_index.md`. **Always diff a "preserved customized" artifact against the shipped template before believing the label** — `--force` is correct whenever the diff is pure version drift, and leaving it is an active inconsistency, not a safe default.
- **Ad-hoc measurement of a versioned schema reproduces the schema's own bug.** Auditing block versions with `grep -o 'DEVLOG:START v[0-9.]*'` silently classified all seven pre-0.2.0 installs as *having no block* — their sentinels predate the version stamp, so there was nothing to match. Failure mode was a confident wrong count, not an error. Same shape as the `sha256` overloading: a reader treating "field absent" as "thing absent." `status` gets this right ("convention block predates the version stamp"); throwaway scripts won't. Prefer the shipped reader over a fresh regex when measuring anything the project has versioned.
- **Defensive code introduces new failure surfaces.** Each "make this safer" pass on the install pipeline (PR #10 preflight, PR #11 hashing/reconciliation) introduced its own bugs that the next Copilot round caught. The pattern: new I/O without `try/except`, new schema fields without explicit encoding, new walks that assume the package is intact. Treat every defensive addition as a new failure site that itself needs testing.
- **A review comment is evidence, not truth.** Especially on generated or versioned artifacts, a PR thread can go stale while the branch keeps moving. The right first move is to inspect the current file state and compare it to the canonical source (`pyproject.toml`, `__version__`, manifest, etc.); sometimes the correct fix is an evidence-backed no-op, and that decision still counts as blog-worthy work.

## Landscape / competitors

- **Commit-driven journals** (DevDiary, DevLog-by-zeshama, AI Commit) — reconstruct narrative post-hoc from git metadata. Lossy by design; quality capped by commit message quality.
- **Changelog generators** (conventional-changelog, git-cliff, semantic-release) — structured release notes, not narrative. Different audience (upgraders vs. evaluators).
- **Manual markdown diaries** — validate demand but fail on sustainability (human discipline as write trigger).
- **Agent-context standards** (AGENTS.md, CLAUDE.md) — devlog's substrate, not competitors. AGENTS.md convergence trend worth tracking.
- **GitHub Agentic Workflows (gh-aw)** — platform-triggered agent tasks; plausible alternative trigger model for devlog entries.
