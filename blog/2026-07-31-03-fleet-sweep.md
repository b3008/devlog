## What changed

The [audit](2026-07-31-01-fleet-upgrade-audit.md) found the fleet four releases
behind and a bug that would have orphaned the legacy index in 16 of 24 projects.
With 0.6.1 in hand, the sweep ran: `devlog migrate` in all 24, then
`devlog install --ai claude` in the 9 that carry a local install.

Result: **1,082 entries** rewritten to OKF frontmatter, 24 indexes renamed
`_index.md` → `index.md`, zero orphans left behind, and a final pass confirming
25/25 conformant.

```console
$ for repo in ...; do (cd $repo && devlog migrate --check); done
OKF conformant: 25    non-conformant: 0
```

The 9 locally-installed projects now report cleanly:

```
REPO                 MANIFEST   BLOCK      INDEX    CMDS
CV                   0.6.1      v0.6.1     OKF      4
claudeESMParser      0.6.1      v0.6.1     OKF      4
PianoDay             0.6.1      v0.6.1     OKF      4
...
```

## Why it matters

This is the first time devlog has been operated as a *fleet* rather than as a
tool you run in the project you happen to be sitting in. Nearly every design
assumption it carries — config-driven paths, cwd-scoped status, reinstall-as-upgrade
— was written from inside a single warm repo. Running it across 24 at once is what
made the gaps legible, and two of them only appeared during execution.

## Surprises

**A tenth of the fleet isn't version-controlled.** Ten of the 24 project
directories have no `.git` at all — scratch projects, a TouchDesigner sketch, an
accounting tool. My progress counter read `git status --porcelain | wc -l`, which
returns 0 for both "clean" and "not a repo", so ten projects reported `dirty 0→0`
after a migration that had just rewritten every file in them. The number was
right for the wrong reason, twice over.

The migration itself was fine, and for a reason the code already anticipated:
`_git_mv()` tries `git mv` and falls back to `Path.rename`. That fallback was
written for untracked files; it turns out to be carrying a tenth of the fleet.
But it does mean **for ten projects there is no undo** — the blog *is* the record,
and nothing versions it. That reframes an assumption the project has been making
since the beginning: entries are described as durable and git-versioned, and for
40% of the places devlog is installed, only the first half is true.

**One project has 471 entries.** PianoDay's migration showed 477 changed files
and I went looking for the bug. There wasn't one — 471 of them are blog entries,
against 34 in devlog's own repo. Sis2 has 298. The three largest projects hold
more than three quarters of the fleet's entries.

That's a scale nothing in the tool was designed for. `build_index()` renders one
flat list, so PianoDay's index is 471 lines of chronological links with no
grouping, no year headers, and no way to find anything. The convention's own
advice about `learned.md` — that a flat file stops being readable long before it
looks large, and the fix is structure, not trimming — applies squarely to the
index and has never been noticed, because dogfooding on a 34-entry blog never
gets close to the limit. The "epoch distillation past ~20 entries" open thread
turns out to have been describing a problem the fleet passed a long time ago.

## What's next

- **Merge 0.6.1.** Nine projects are now stamped `v0.6.1` while the released tool
  and the global block are at `0.6.0`, so `devlog status` in those projects will
  correctly warn that the install is newer than the tool. Harmless — the template
  content is byte-identical between the two, only the stamp differs — but it
  resolves only when 0.6.1 lands on `main` and `uv tool upgrade` runs.
- **The 24 projects have uncommitted changes.** Deliberately left that way; a
  sweep that rewrites 1,082 files across other people's repositories should not
  also decide what gets committed. Ten of them can't be committed at all.
- **Index structure at scale.** A 471-line flat index is the concrete case for
  grouping (by year, or by epoch) that the retrieval thread has been circling.
  Worth measuring before designing: an index nobody can navigate fails the same
  way an unreadable `learned.md` does.
